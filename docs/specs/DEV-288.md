## 1. Проблема и цель

**Проблема.** Модуль 152-ФЗ отсутствует на живом сайте:

- `plugins/idpg-core/includes/class-privacy.php` — есть в HEAD, **удалён из рабочего
  дерева** и **не подключён** в `idpg-core.php`.
- По `tests/test-registration-form.php:395` модуль переносили в `idpg-city-admin`
  (DEV-271), но этот плагин **не активен**, а его файлы **отсутствуют на диске**
  (`plugins/*` в `.gitignore`, в git не попадали, в HEAD нет).

**Следствия сейчас:**

| Механизм | Состояние |
|---|---|
| Чекбокс «Согласен на обработку ПДн» при регистрации | выводится (`page-login.php`, fallback-имя `idpg_pdn_consent`) |
| REST-проверка согласия | есть — без галочки `400 pdn_consent_required` (`class-rest-auth.php:423`) |
| **Запись факта согласия** | **нет** — `record_consent()` не вызывается (`class_exists('IDPG_Privacy')` ложно) |
| Cookie-баннер | **нет** (assets удалены, в теме нет упоминаний) |
| Права субъекта (выгрузка / удаление / отзыв) | **нет** |
| Страница «Политика конфиденциальности» | опубликована (ID 114), шаблон темы есть |

**Цель.** Написать модуль приватности заново (не восстанавливая из git) и дать ему
админ-интерфейс **вкладкой на существующей странице «IDPG»** (`idpg-widget-areas`).

## 2. Решение

### 2.1. Модуль `IDPG_Privacy` (новый файл, пишем с нуля)

`plugins/idpg-core/includes/class-privacy.php`, подключение — `require_once` в
`idpg-core.php` (блок подключений рядом с `class-user-purge.php`).

Публичный контракт (совместим с прежним, чтобы не ломать `class-rest-auth.php` и
`page-login.php`, которые уже ссылаются на `IDPG_Privacy`):

| Член | Назначение |
|---|---|
| `const CONSENT_FIELD = 'idpg_pdn_consent'` | имя чекбокса/параметра |
| `const CONSENT_VERSION` | редакция документов (строка, напр. `'2026-10-20'`) |
| `record_consent( $user_id, $source )` | запись согласия в user meta `idpg_pdn_consent` (дата, редакция, источник, хеш IP); снимает прежний отзыв |
| `has_consent( $user_id )` | `false`, если согласия нет **или** оно отозвано |
| `get_consent( $user_id )` | массив записи о согласии |
| `withdraw_consent( $user_id )` | запись отзыва в `_idpg_pdn_consent_withdrawn` (отдельная метка, факт «дано и отозвано» хранится) |
| `is_withdrawn( $user_id )` / `get_withdrawal( $user_id )` | чтение отзыва |
| `get_consent_version()` | текущая редакция |
| `hash_client_ip()` | `wp_hash( REMOTE_ADDR )` — сырой IP не хранится |
| static `instance()` | синглтон, вешает хуки в конструкторе |

Хуки модуля:

- **Cookie-баннер:** `wp_enqueue_scripts` (ассеты), `wp_footer` (разметка),
  `template_redirect` (обработка POST выбора: cookie `idpg_cookie_consent` = `all` |
  `necessary`, срок — год). Работает без JS (POST + nonce) и с JS.
- **Права субъекта:** `template_redirect` — обработка запроса на выгрузку/удаление
  и отзыва согласия; `admin_post_idpg_privacy_self_export` — само-выгрузка
  авторизованного пользователя.
- **Админ-обработчики:** `admin_post_idpg_privacy_export` / `_preview` / `_delete` —
  выгрузка и удаление по запросу субъекта (только `manage_options` + nonce).
- **События:** `do_action('idpg_privacy_consent_record', $user_id, $record)`,
  `idpg_privacy_consent_withdrawn`, фильтры `idpg_privacy_consent_version`,
  `idpg_privacy_banner_text` и т.п. (префикс `idpg_`).

Блок прав субъекта (`render_subject_tools()`) выводится **фильтром `the_content`**
только на странице политики (её ID — из опции `wp_page_for_privacy_policy`, fallback —
страница со slug `privacy`). Шаблон `page-privacy.php` **не трогаем** (там только текст
документа через `idpg_core_legal_render()`).

### 2.2. Вкладка «Приватность» на странице «IDPG» (расширение темы — аддитивно)

Тема отдаёт свой список вкладок плагину фильтром. Правки `inc/widget-areas.php` —
**только добавление** (логика vкладок list/form не меняется):

1. В `idpg_widget_areas_admin_page()` после `$tab`:
   `$extra_tabs = apply_filters( 'idpg_widget_areas_admin_tabs', array() );`
   — массив `slug => array( 'label' => string, 'callback' => callable )`.
2. Допустимые вкладки: `array_merge( array('list','form'), array_keys($extra_tabs) )`
   в проверке `in_array()`.
3. Вывод ссылок вкладок: после `#tab-idpg-form` — цикл по `$extra_tabs`
   (`a.idpg-tab`, `id="{slug}"`, `href="#idpg-{slug}"`, активность по `$tab`).
4. Вывод контента: после `#idpg-form` — цикл `<div id="idpg-{slug}"
   class="idpg-tab-in js-idpg-tab-item…">` + `call_user_func( $callback )`.
5. Инлайн-JS темы: регулярка cookie `tab-idpg=(list|form)` → универсальная
   (`tab-idpg=([a-z0-9_-]+)`), чтобы новая вкладка запоминалась.

Плагин регистрирует вкладку фильтром:

```php
add_filter( 'idpg_widget_areas_admin_tabs', function ( $tabs ) {
    $tabs['privacy'] = array(
        'label'    => __( 'Приватность (152-ФЗ)', 'idpg-core' ),
        'callback' => array( IDPG_Privacy::instance(), 'render_admin_tab' ),
    );
    return $tabs;
} );
```

`render_admin_tab()` рисует в стиле страницы (`.idpg-option-field`, карточки,
`idpg-ico-help`): сводка согласий, список запросов субъектов, блок выгрузки/удаления,
кнопки. Формы вкладки — свои nonce (`idpg_privacy_admin`) и `manage_options`;
обработка — на `admin_init` (модуль, не тема), после сохранения — редирект на
`admin.php?page=idpg-widget-areas&tab=privacy&idpg_msg=…`.

### 2.3. Интеграция с существующим кодом (не ломая)

- `class-rest-auth.php` и `page-login.php` уже вызывают `IDPG_Privacy`, когда класс
  есть — после подключения модуля запись согласия заработает без их правок.
- Куки автоопределения города (`class-city-filter.php`) — **вне рамок** (см. §4).

## 4. Границы (что НЕ делаем)

- **Не восстанавливаем** `class-privacy.php` из git и **не возвращаем** `idpg-city-admin`.
- **Не трогаем** автоопределение города по IP (`class-city-filter.php`, ip-api.com /
  ipapi.co) — вопрос трансграничной передачи вынесен отдельно (карточка владельца),
  в этой задаче не решается.
- Не меняем логику `class-rest-auth.php` и `page-login.php` (они уже готовы к классу).
- Не переписываем вкладки `list`/`form` темы и не меняем их поведение/разметку —
  только добавляем точки расширения.
- Не делаем собственный экран `admin.php?page=idpg-privacy` — UI только вкладкой.
- Не добавляем новых настроек в другие модули; не трогаем Clearfy/AIOWP/Yoast.
- Не переносим проприетарные стили Clearfy Pro; вкладка использует существующие
  классы страницы (`.idpg-*`).

## 6. Обратная проба

- **Замер «до»:** на момент старта `IDPG_Privacy` отсутствовал (не подключён), новых
  тестов не было. После написания тестов и до подключения модуля они падали
  (`class_exists` ложно / фильтр пуст).
- **Замер «после»:** `Test_Privacy` — 17 тестов / 45 утверждений зелёные;
  полный прогон плагина — **520 тестов / 1426 утверждений** (было 502 / 1371;
  +18 тестов: 11 модуль + 6 вкладка + 1 удалённый skip в test-registration-form).
- **Мутации (прогнано, все пойманы):**
  1. убрать проверку `is_withdrawn()` из `has_consent()` → `test_has_consent_false_after_withdraw` (1 падение);
  2. убрать `delete_user_meta()` отзыва в `record_consent()` → `test_record_clears_withdrawal`;
  3. переименовать хук фильтра вкладки → `Test_Privacy_Tab` (2 падения);
  4. снять `current_user_can` в `render_admin_tab()` → `test_render_admin_tab_guards_capability`;
  5. переименовать ключ `given` → `given_at` → `test_record_consent_stores_meta` + `test_consent_is_recorded_with_organizer_source` (ошибки);
  6. убрать `wp_nonce_field()` из баннера → `test_banner_markup_present`.
- **Подтверждение отсутствия регрессий:** полный PHPUnit — 520 / 1426, падений нет;
  PHPCS модуля/тестов/`idpg-core.php` (стандарт плагина) и `inc/widget-areas.php`
  (стандарт темы) — exit 0. `test-registration-form.php` больше не пропускается и
  проходит на новом контракте.
