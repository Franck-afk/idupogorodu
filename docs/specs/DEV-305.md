>
> **Приоритет:** P0.
> **Решения владельца (20.10.2026):**
> 1. Источник базы — **DB-IP Lite**, набор по РФ (CSV).
> 2. Таблица — через существующий `dbDelta` при активации плагина; **импорт — кнопкой**
>    на странице «IDPG» (вкладка, точка расширения DEV-288).
> 3. Внешние сервисы (`ip-api.com`, `ipapi.co`) — **удалить вызовы полностью**

## 1. Проблема и цель

**Проблема.** Определение города по IP уходит на зарубежные сервисы:

- `plugins/idpg-core/includes/class-city-filter.php:480` — `request_ip_data()` шлёт
  `wp_remote_get()` на `https://ip-api.com/json/{ip}` и, при неудаче, на **`http://ip-api.com/json/{ip}`**
  (открытый HTTP), а также на `https://ipapi.co/{ip}/json/`.
- IP посетителя **передаётся за пределы РФ** (сервисы в США) и по незащищённому каналу —
  нарушение **242-ФЗ** (трансграничная передача персональных данных).

**Следствия сейчас:**

| Механизм | Состояние |
|---|---|
| Автоопределение города по IP | работает через ip-api.com / ipapi.co (трансгранично) |
| Фолбэк на HTTP | да, при недоступности HTTPS |
| Кэш результата | transient `idpg_city_ip_{md5}`, 24ч/12ч/10мин |

**Цель.** Заменить внешние вызовы на запрос к **локальной БД диапазонов IP → регион РФ**
(`{prefix}idpg_geo_ranges`), обновляемой владельцем. IP не покидает сервер.

## 2. Решение

### 2.1. Таблица `{prefix}idpg_geo_ranges`

Создаётся `dbDelta` при активации (существующий `idpg_core_activate()`), рядом с
`idpg_core_create_subscribers_table()`. Функция — `idpg_core_create_geo_ranges_table()`.

```sql
CREATE TABLE {prefix}idpg_geo_ranges (
    id BIGINT(20) UNSIGNED NOT NULL AUTO_INCREMENT,
    ip_start BIGINT(20) UNSIGNED NOT NULL,
    ip_end BIGINT(20) UNSIGNED NOT NULL,
    region VARCHAR(191) NOT NULL DEFAULT '',
    PRIMARY KEY  (id),
    KEY range_lookup (ip_start, ip_end)
) {charset_collate};
```

- `ip_start` / `ip_end` — границы диапазона IPv4 как **целое** (32-битное число).
  **Имена колонок — `ip_start`/`ip_end`, а не `start`/`end`:** `start` и `end` —
  зарезервированные слова MySQL, из-за которых `dbDelta` (`WordPress.DB` парсер)
  возвращает пустой результат и таблица молча не создаётся. Проверено кодом.
- IPv6 не поддерживается: 128-битное число не помещается в BIGINT, адрес → `-1` (см. §4).
- `region` — название субъекта РФ (после локализации через `region_aliases()`,
  хранится по-русски: `Удмуртская Республика`).

### 2.2. Модуль `IDPG_Geo_Ranges` (`class-geo-ranges.php`, новый)

Тонкий слой над таблицей. Публичный контракт:

| Член | Назначение |
|---|---|
| `const TABLE = 'idpg_geo_ranges'` | имя таблицы без префикса |
| `const OPT_UPDATED` / `const OPT_ROWS` | опции с датой и числом строк последнего импорта |
| `const IMPORT_ACTION = 'idpg_geo_import'` | действие nonce формы импорта |
| `const TAB_SLUG = 'geo'` | слаг вкладки на странице «IDPG» |
| `static table_name()` | `$wpdb->prefix . self::TABLE` |
| `static table_exists( $fresh = false )` | есть ли таблица (проверка через `DESCRIBE`, кэш в статике; `$fresh` сбрасывает) |
| `static ip_to_long( $ip )` | IPv4 → int (32 бита); вернуть `-1` для IPv6/невалидного |
| `static lookup_region( $ip )` | `SELECT region … WHERE ip_start <= %d AND ip_end >= %d LIMIT 1`; пусто → `''` |
| `static import_csv( $path )` | построчный импорт DB-IP CIDR/range CSV; `TRUNCATE` перед импортом; `['rows'=>int,'skipped'=>int]` или `['error'=>string]` |
| `static parse_csv_line( $line )` | разбор строки CSV → `[ip_start, ip_end, region]` или `null` |
| `static boundary_to_long( $value )` | граница (число / CIDR / IPv4) → int |
| `static region_aliases()` / `static localize_region()` | карта англ.→рус. (фильтр `idpg_geo_region_aliases`) и локализация при импорте |
| `static count()` | число диапазонов (для сводки в админке) |
| `static instance()` | синглтон (вешает админ-вкладку и обработчик импорта) |

**SQL-безопасность:** только `$wpdb->prepare()`; никакой конкатенации значений.

### 2.3. Импорт DB-IP Lite (РФ) — админ-вкладка «Гео (IP→регион)»

Плагин регистрирует вкладку на странице «IDPG» тем же фильтром, что DEV-288:
`idpg_widget_areas_admin_tabs` → `['geo' => …]`.

`render_admin_tab()`:

- сводка: число диапазонов, дата последнего импорта (опции `idpg_geo_ranges_updated` / `idpg_geo_ranges_rows`);
- форма загрузки CSV (`<input type="file" name="idpg_geo_csv">`), `enctype="multipart/form-data"`,
  поле nonce `idpg_geo_import`, кнопка «Импортировать»;
- обработчик — на `admin_init`, right `manage_options` + `check_admin_referer( 'idpg_geo_import' )`;
  файл читается через `$_FILES`, проверяется `wp_check_filetype()`, парсится `import_csv()`,
  редирект на `admin.php?page=idpg-widget-areas&tab=geo&idpg_msg=…`.

Формат CSV: DB-IP Lite range-набор — строки `начальный_IP,конечный_IP,"Регион","Страна"`.
Импортёр принимает оба вида границ (IPv4-строки и CIDR) и берёт только строки страны `RU`
(страна определяется наличием региона, заданного в РФ-выгрузке; при полном наборе — по коду `RU`).

### 2.4. Замена внешних вызовов в `class-city-filter.php`

- Удаляются: `request_ip_data()`, `normalize_services()`, ветки `ip_api`/`ipapi_co`,
  константа/логика выбора внешних сервисов.
- `lookup_city_id_by_ip()` меняет источник: берёт `IDPG_Geo_Ranges::lookup_region( $ip )`,
  затем `match_city_term( '', $region )`.
- Логика кэша (transient `idpg_city_ip_{md5}`, TTL ok/miss/fail, lock) — **сохраняется**;
  меняется только «источник ответа». При пустой/отсутствующей таблице — `fail`-кэш
  (10 минут), как при недоступном сервисе.
- `allowed_ip_services()`: настройка виджета `ip_service` со значениями
  `ip_api`/`ipapi_co`/`none` заменяется на `local`/`none`. Значение `local` — использовать
  локальную БД; `none` — автоопределение выключено (**фолбэк `services=none`**).
  Список сервисов виджета (`IDPG_City_Selector_Widget::ip_services()`) обновляется:
  `none` («Не определять») и `local` («Локальная база (РФ)»). Дефолт — `local`.
- `match_city_term( $city, $region )` — ветка сопоставления региона через
  `region_names_match()` **уже существовала** и не переписывается: при пустом `$city`
  регион сопоставляется с терминами-регионами, возвращается дефолтный город региона
  или первый город региона.
- **Кросс-языковой маппинг вынесен на импорт, а не в `match_city_term`.** DB-IP хранит
  регионы по-английски (`Udmurt Republic`), термины `city` — по-русски. `region_names_match`
  сравнивает транслитерацию/нормализацию и **не** переводит «Udmurt Republic» ↔
  «Удмуртская Республика» (общего корня нет). Поэтому при импорте
  `IDPG_Geo_Ranges::localize_region()` переводит регион по карте `region_aliases()`
  (фильтр `idpg_geo_region_aliases` для расширения владельцем), и в таблице уже лежит
  русское имя. `match_city_term` работает с русским регионом как раньше.

### 2.5. Настройки/виджет

`IDPG_City_Selector_Widget` — в `form()`/`update()` заменить варианты сервиса. Так как
класс виджета большой, правится **только** список опций и дефолт (аддитивно), логика цепляется
на новые ключи `local`/`none`.

## 4. Границы (что НЕ делаем)

- **Не поддерживаем IPv6** — 128-битные границы не влезают в BIGINT; IPv6-адреса → `-1` → не
  определяем (фолбэк на город по умолчанию). При необходимости — отдельная задача.
- **Не парсим бинарные/MMDB-базы** (GeoIP2/DB-IP mmdb) — только CSV.
- Не храним `city_id` в таблице (маппинг — в PHP через `match_city_term`).
- Не добавляем собственный экран `admin.php?page=idpg-geo` — UI только вкладкой.
- Не меняем `IDPG_GeoService` (фасад), `IDPG_City_URL`, `filter_by_city()` и логику cookie города.
- Не трогаем права субъекта/приватность (DEV-288).
- Не наполняем БД данными в этой задаче — наполнение делает владелец кнопкой импорта.
