## 1. Общая сводка

Личный кабинет организатора (`/organizer/`) — ключевой пользовательский интерфейс проекта «Иду по городу». Он позволяет организаторам создавать и управлять событиями, площадками и профилем. Реализован как **гибридная архитектура**: серверный рендеринг каркаса + JavaScript для динамики и REST API для данных.

**Статус:** функционально работает, покрыт тестами (273 теста / 945 утверждений, падений 0). Есть открытые задачи по расширению функциональности (реквизиты, верификация, часы работы площадок).

## 2. Архитектура

### 2.1. Маршрутизация

Маршрут регистрирует `IDPG_Organizer_URL` (rewrite + query vars + template_include), не опирается на запись WP:

| URL | Назначение | Шаблон |
|---|---|---|
| `/organizer/` | Кабинет (раздел по умолчанию — dashboard) | `page-organizer.php` |
| `/organizer/dashboard/` | Дашборд | тот же шаблон |
| `/organizer/events/` | Список событий | тот же шаблон |
| `/organizer/venues/` | Список площадок | тот же шаблон |
| `/organizer/profile/` | Профиль организатора | тот же шаблон |
| `/organizer/event/new/` | Создание события | `page-organizer-event.php` |
| `/organizer/event/{id}/` | Редактирование события | `page-organizer-event.php` |
| `/organizer/venue/new/` | Создание площадки | `page-organizer-venue.php` |
| `/organizer/venue/{id}/` | Редактирование площадки | `page-organizer-venue.php` |

**Query-переменные:** `idpg_organizer_section`, `idpg_organizer_page`, `idpg_organizer_event`, `idpg_organizer_venue`.

### 2.2. Роли и доступ

| Роль | Доступ в кабинет | Редирект после входа |
|---|---|---|
| `event_organizer` | Да | `/organizer/` |
| `administrator` | Да (но не редиректит) | `wp-admin` |
| `editor` | Да (но не редиректит) | `wp-admin` |
| `subscriber` | Нет (403) | — |
| Гость | Нет (302 → `/login/`) | — |

Проверка: `IDPG_Organizer_URL::get_access_decision()` → `guest`/`denied`/`allowed`. Шаблон дублирует логику fallback'ом на случай отключения плагина.

**Роль `event_organizer`:** создаётся `IDPG_Roles` (singleton, `ROLE_VERSION = 7`), имеет caps на `event` (свои записи), `venue` (свои записи), `upload_files`. Не имеет `edit_others_posts` — скоуп работает через это.

### 2.3. Меню кабинета

Единый источник — `idpg_organizer_menu()` (`inc/organizer-menu.php`). Четыре пункта:

1. **Дашборд** (`dashboard`, order 10)
2. **Мои события** (`events`, order 20)
3. **Площадки** (`venues`, order 25, DEV-50)
4. **Профиль** (`profile`, order 30, DEV-73)

Расширение через фильтр `idpg_organizer_menu_items`. Каждый пункт требует template-part `template-parts/organizer/section-{slug}.php`.

### 2.4. REST API

Пространство: `idpg/v1`. Класс: `IDPG_REST_Organizer`.

| Метод | Маршрут | Описание |
|---|---|---|
| GET | `/organizer/stats` | Счётчики событий по статусам |
| GET | `/organizer/events` | Список событий (фильтр, пагинация) |
| GET | `/organizer/events/{id}` | Одно событие |
| POST | `/organizer/events` | Создать черновик |
| PUT | `/organizer/events/{id}` | Обновить черновик/отклонённое |
| POST | `/organizer/events/{id}/submit` | Отправить на модерацию |
| DELETE | `/organizer/events/{id}` | Удалить черновик/отклонённое |
| PUT | `/organizer/profile` | Сохранить профиль |
| GET | `/organizer/venues` | Список площадок |
| GET | `/organizer/venues/{id}` | Одна площадка |
| POST | `/organizer/venues` | Создать площадку |
| PUT | `/organizer/venues/{id}` | Обновить площадку |
| DELETE | `/organizer/venues/{id}` | Удалить площадку |

**Ключевые решения REST:**
- **Скоуп только свои события** — чужое → 403 (не 404, чтобы не выдавать факт существования).
- **Жизненный цикл** — `draft`/`rejected` можно править и удалять; `pending`/`publish` — нельзя (409/403).
- **Модерация не дублируется** — `IDPG_Event_Moderation` применяется автоматически при submit.

### 2.5. JavaScript

Файл: `themes/idpg_core/assets/js/organizer.js` (~827 строк).

**Функции:**
- Переключение разделов без перезагрузки (`history.pushState`, `popstate`).
- Загрузка статистики (кэш промиса — один запрос на страницу).
- Список событий с фильтром и пагинацией (состояние в URL).
- Список площадок.
- Сохранение профиля через `fetch` + `PUT /organizer/profile` (fallback на обычный POST).

**No-JS поддержка:** прямой заход по URL работает серверно; профиль сохраняется через POST (DEV-73). Форма события и площадки без JS — только чтение/создание через POST в venue.

### 2.6. Стили

| Файл | Размер | Подключён в `style.scss` | Примечание |
|---|---|---|---|
| `pages/_cabinet.scss` | ~1400 строк | Да | `.dashboard__*`, `.idpg-org-*` |
| `pages/_dashboard.scss` | ~800 строк | Да | Часть кабинета |
| `pages/_create-event.scss` | ~900 строк | Да | Форма события |
| `pages/_venue-form.scss` | ~200 строк | Да | Форма площадки |
| `pages/_organizer.scss` | ~600 строк | **Нет** | Отдельный `organizer.css` |
| `assets/css/organizer.css` | ? | Вешается через `wp_enqueue_style` | 48 правил `.idpg-org-*` |

**Важно:** `pages/organizer` и `pages/venue-form` **не подключены** в `style.scss` осознанно — их правила отдаются отдельным `organizer.css`, который вешается только на `/organizer/*`.

## 3. Функциональные разделы

### 3.1. Дашборд (`section-dashboard.php`)

- Карточки: «Всего событий», «Опубликовано», «На модерации», «Черновики».
- Данные: `GET /idpg/v1/organizer/stats` (JS).
- Кнопка «+ Создать событие» — обычная ссылка, работает без JS.
- `noscript` — уведомление, что счётчики требуют JS.

### 3.2. Мои события (`section-events.php`)

- Фильтры по статусам: all, publish, pending, draft, rejected (счётчики на вкладках).
- Таблица: событие (постер + название + ссылка), статус (бейдж), просмотры.
- Пагинация: 20 на страницу, состояние в URL (`?status=&p=`).
- Кнопка «+ Создать событие».
- Загрузка постеров: batch-запрос к `/wp/v2/media` (кэш URL по ID).

### 3.3. Площадки (`section-venues.php`, DEV-50)

- Список: `GET /idpg/v1/organizer/venues`.
- Таблица: название, тип, адрес.
- **Чужие опубликованные площадки видны** (`is_own: false`) — чтобы можно было выбрать в событии, но правки нет.
- Форма создания/правки: `page-organizer-venue.php` + `venue-form.php`.
- Работает **без JavaScript** (POST с nonce).

### 3.4. Профиль (`section-profile.php`, DEV-73)

- Поля: имя в системе, email (только чтение), организация, контактное лицо, телефон, аватар.
- **Email нельзя изменить** — требует подтверждения (не реализовано).
- Два режима сохранения:
  - **JS:** `fetch` + `PUT /idpg/v1/organizer/profile`.
  - **No-JS:** POST на `page-organizer.php` + Post/Redirect/Get.
- Санитайз: HTML вырезается, длина ≤ 190.

### 3.5. Форма события (`page-organizer-event.php`, G5)

- Создание и редактирование события.
- Данные подставляются сервером из `IDPG_REST_Organizer::format_event()`.
- **Без JavaScript изменить нельзя** — только чтение.
- Загрузка постера и импорт из файла **не реализованы** (блоки в SCSS есть, но скрыты).

## 4. Безопасность

| Угроза | Защита |
|---|---|
| Несанкционированный доступ | `get_access_decision()` — 403/302; шаблон дублирует fallback |
| CSRF (профиль) | `wp_nonce_field('idpg_organizer_profile')` |
| CSRF (REST) | `X-WP-Nonce` + REST nonce |
| XSS | `esc_html`, `esc_attr`, `esc_url` на выводе; `sanitize_text_field` на входе |
| Подделка аватара | Проверка `wp_attachment_is_image()` |
| Доступ к чужим событиям | Скоуп по `post_author` → 403 |
| Правка pending/publish | 409/403 в REST |
| SQL-инъекция | WP_Query + prepared statements |
| Админ-меню организатора | Скрыто `hide_unnecessary_menus()` |

**Скоуп медиа:** `IDPG_Organizer_Scope` ограничивает медиатеку только своими вложениями (`pre_get_posts`, `rest_attachment_query`).

## 8. Риски и проблемы

### 8.1. Безопасность

- **Email организатора нельзя сменить** — это хорошо для защиты, но плохо для UX. DEV-73 оставил смену email на потом.
- **Роль `event_organizer` и `default_role`:** защита `ensure_safe_default_role()` (DEV-98) есть, но если плагин отключён, роль остаётся у пользователей.
- **Соц-вход:** DEV-51 (соц-вход не выдаёт роль `event_organizer`) — статус нужно проверить в бэклоге.

### 8.2. Функциональность

- **Форма события без JS — только чтение.** Это осознанное решение, но может отсеять часть пользователей.
- **Загрузка постера и импорт — не реализованы.** Организатор не может загрузить картинку к событию.
- **Площадки: чужие видны, но нельзя редактировать** — корректно, но UI не объясняет, почему некоторые площадки без ссылки.

### 8.3. Производительность

- **Batch-запрос постеров** — хорошо, но при 20 событиях с постерами будет 2 запроса: events + media.
- **Счётчики stats** — кэшируются промисом, хорошо.
- **Нет кэширования на сервере** — каждый запрос к `/organizer/stats` делает `WP_Query`.

### 8.4. SEO / Инфраструктура

- **Страница `/organizer/` создана темой** (`idpg_core_create_organizer_page()`) — нужна для крошек и исключения из sitemap Yoast.
- **Редирект с `/login/`** живёт в плагине (`template_redirect`), а не в шаблоне — это задокументировано как грабля.
