# План безопасного рефакторинга

**Статус:** аудит и планирование; функциональный код пока не менялся.
**Цель:** улучшить сопровождаемость без намеренных изменений поведения, публичных REST-контрактов, URL, метаданных и схемы хранения.

## Вывод аудита

Проект — WordPress-сайт из плагинов `idpg-core` / `idpg-auth` и темы `idpg_core` / дочерней темы. В ядре уже есть PHPUnit-наборы, тесты auth, PHPCS с baseline, CSS-сборка и проверки JS/SCSS. Это хорошая основа для постепенного рефакторинга, но не основание переписывать систему целиком одним изменением.

Основной риск — крупные компоненты с несколькими зонами ответственности: `class-rest-organizer.php` (2138 строк), `class-rest-api.php` (1525), `class-banner-settings.php` (1397), `class-event-fields.php` (1352), `class-current-event-banner.php` (1216), `class-organizer-url.php` (1191), `class-rest-auth.php` (974), `class-privacy.php` (926). Размер — сигнал для анализа, но не доказательство дефекта и не причина механически дробить классы.

Инициализация ядра также централизована в `plugins/idpg-core/idpg-core.php`: большой список `require_once`, создание компонентов на разных хуках и отдельные исключения для ранней регистрации. Здесь особенно важен порядок загрузки WordPress hooks. В теме `functions.php` уже стал тонким загрузчиком отдельных файлов `inc/functions-*.php`; это состояние следует сохранить, а не запускать повторную реорганизацию без выгоды.

В документации есть расхождения между файлами и историческими статусами: например, `docs/STATUS.md` содержит заметку, что раздел о кабинете организатора устарел, а `docs/PROJECT.md` объединяет актуальные сведения с историческим бэклогом. При правках надо сверять факт по коду и тестам и исправлять документацию в том же этапе.

## Ограничения проверки в этой среде

На момент аудита `php` и `composer` не обнаружены в PATH; зависимости PHPUnit также не подтверждены. Поэтому сейчас нельзя честно заявить о прохождении PHP-тестов, PHP lint или PHPCS. Перед изменением PHP-кода надо установить/подключить подходящую среду и получить baseline запуска тестов. Не менять PHP исключительно ради форматирования, пока нет возможности проверить результат.

## Принципы

1. Малые вертикальные этапы, каждый со своим тестом и понятным откатом.
2. Сначала зафиксировать существующее поведение тестами; затем менять внутреннее устройство.
3. Не менять REST-форматы, публичные хуки/фильтры, URL/rewrite, права, мета-ключи и миграции без отдельного согласования.
4. Не удалять код только на основании отсутствия видимых вызовов: проверить динамические хуки WordPress, шаблоны, фильтры, дочернюю тему и внешние интеграции.
5. Не трогать собранные файлы вручную; сохранять порядок CSS cascade и регистрацию скриптов.
6. Каждый этап сопровождается тестами, diff-review и актуализацией документации.

## Этапы

### 0. Зафиксировать baseline — текущий этап

- Сверить дерево, конфигурации, CI и реальные команды тестов.
- Инвентаризировать крупные модули и разрывы документации.
- Подготовить безопасный порядок изменений. **Выполнено:** этот документ.
- Открытый пункт: получить успешный baseline полного PHPUnit/PHPCS/SCSS/JS CI в среде с PHP/Composer и установленными зависимостями.

### 1. Проверки и договорённости

- Поднять локальные команды из `plugins/idpg-core/phpunit.xml.dist`, `plugins/idpg-auth/phpunit.xml.dist`, PHPCS-конфигов и `themes/idpg_core/package.json`.
- Убедиться, что существующие тесты реально проходят до рефакторинга; отдельно записать известные падения и тесты, требующие WordPress test suite.
- Добавить characterization-тесты только там, где дальнейшее выделение функций/классов оставляет важное поведение незафиксированным.
- Составить карту хуков и зависимостей для первого выбранного компонента.

### 2. Упростить bootstrap ядра

- Разобрать `idpg-core.php` на загрузку файлов и явную регистрацию/инициализацию модулей, сохраняя точный порядок хуков и раннюю инициализацию баннера.
- Не вводить автозагрузчик или контейнер зависимостей без доказанной необходимости: проект поддерживает PHP 7.4.
- Покрыть порядок инициализации тестом. Изменения по одному логическому блоку.

### 3. Декомпозиция крупных компонентов

- Выбирать компонент по сложности изменений и дублированию, а не по числу строк.
- Предварительно рассматривать REST organizer: разделить регистрацию маршрутов, валидацию/санитизацию и операции данных, сохранив текущий класс как тонкий фасад при необходимости.
- Аналогично оценить REST API и настройки баннера после построения карты ответственности.
- Сохранять имена маршрутов, аргументы, статусы ответов, capability checks, nonce и формат JSON побайтно совместимыми там, где это возможно.

### 4. Уменьшить дублирование

- Сравнить общие правила в REST/auth, поля/метабоксы, обработку расписаний и медиа.
- Выносить общую логику только при наличии реальных повторов и тестов; избегать чрезмерно универсальных helper-классов.

### 5. Тема и frontend

- Инвентаризировать функции/шаблоны/ассеты и повторяющуюся разметку.
- Добавлять доступные template-parts, устранять дубли JS постепенно.
- После каждого CSS-изменения пересобирать Sass и выполнять `check:css`, lint SCSS/JS и визуальную проверку. Не менять порядок каскада без проверки страниц.

### 6. Завершение и документация

- Повторить полный CI и функциональные smoke-тесты WordPress.
- Сверить API, hooks, настройки, миграции и инструкции развёртывания с реальным кодом.
- Удаление deprecated-кода — только отдельными небольшими изменениями с поиском потребителей и проверкой обратной совместимости.

## Критерии готовности

«Полный рефакторинг» считается завершённым не по числу переписанных файлов, а когда каждый согласованный компонент имеет понятную ответственность, существенные контракты защищены тестами, полный CI проходит, а документация соответствует коду. Любое изменение поведения или публичного контракта выносится из этого рефакторинга в отдельную задачу.
