```php

// Обновлённые ключи и соли: https://api.wordpress.org/secret-key/1.1/salt/
// (ОБЯЗАТЕЛЬНО новые, не из репозитория и не из стенда).

// ... остальные ключи ...

// Отключение правок файлов через админку.
```

## 4. Cron (🔴)

Плагин ставит задачу `idpg_cron_sync_tickets` (каждые 3 часа).

На проде **обязателен системный cron** (WP-Cron на пустом трафике ненадёжен):

```cron
0 */3 * * * /usr/bin/php /var/www/idupogorodu.ru/wp-cron.php >/dev/null 2>&1
# или через wget/curl:
0 */3 * * * curl -s https://idupogorodu.ru/wp-cron.php?doing_wp_cron >/dev/null
```

и константа `DISABLE_WP_CRON` из раздела 1.

## 12. Восстановление git (🔴, DEV-102)

Случай 29.09.2026: индекс репозитория оказался пустым (0 записей при
валидном заголовке DIRC), а `.gitignore` в рабочем дереве был подменён —
49 строк вместо 152. Следствия:

- `git ls-files` возвращал 0 файлов;
- `git status` показывал 250 «удалённых» файлов, которых на диске нет;
- новые файлы не попадали в индекс, часть наших каталогов молча
  игнорировалась;
- работа организатора за 29.09 существовала только на диске.

### Порядок восстановления

1. **Бэкап всего `.git`** целиком — операция необратима, `.git` не удалять.
2. Бэкап БД (`mysqldump`) и файлов перед любыми действиями с индексом.
3. `git log --oneline -10` и `git remote -v` — понять, где остановилась
   история и есть ли remote.
4. Сравнить `.gitignore` в дереве и в HEAD:
   `git diff --no-index <(git show HEAD:.gitignore) .gitignore`.
5. Вернуть `.gitignore` из HEAD: `git checkout HEAD -- .gitignore`.
6. Мягкий сброс: `git reset HEAD` — индекс снова описывает файлы HEAD.
7. `git add -A`, затем обязательно проверить, что не попало лишнее:
   `git status --porcelain`, `git check-ignore -v <путь>`.
8. Коммит, `git push` (без `--force`).

### Проверка перед коммитом

```bash
# свои вендорные ассеты должны ОСТАВАТЬСЯ tracked (DEV-60)
git check-ignore -v themes/idpg_core/assets/js/vendor   # exit=1 — верно
# вендор чужого плагина должен игнорироваться
git check-ignore -v plugins/wp-mail-smtp/vendor         # exit=0 — верно
# тяжёлое не должно попадать в индекс
git status --porcelain --untracked-files=all | wc -l
```

### Локальный мусор

В `.git/info/exclude` (не в `.gitignore` — правило только для этой
машины): черновики вроде `t2.scss`, локальные дампы. Файл остаётся
на диске, но в репозиторий не идёт.

### Состояние на 29.09.2026

- HEAD: `c12921c` (DEV-102), предыдущий — `fdf4ca0` (DEV-60);
- индекс: 305 файлов, рабочее дерево чистое;

## 12.1. Восстановление битого HEAD (🔴, DEV-134)

Случай 30.09.2026: `git status` и `git stash` падали с
`fatal: bad object HEAD`. `refs/heads/master` указывал на `2f5c376`,
но самого объекта в хранилище не было — `.git/objects/2f/` оказался
**пустым каталогом**. Причина: потеря loose-объектов (запись коммита
29.09 22:57 так и не была зафиксирована на диске). Уцелели паки и
индекс (308 записей), рабочее дерево не пострадало.

### Диагностика

```bash
git fsck --full                 # что именно потеряно
git cat-file -t <sha>           # существование конкретного объекта
ls -la .git/objects/2f/         # пусто = объект потерян безвозвратно
git ls-remote origin            # что есть на удалёнке
git verify-pack -v .git/objects/pack/*.idx | grep <sha>
```

Картина сбоя: **5 отсутствующих blob** (все — SCSS, тронутые DEV-87)
плюс битые указатели `refs/heads/master`, `refs/remotes/origin/master`
и `HEAD`. `2f5c376` (DEV-87, этап 5) — **единственный утраченный
коммит**; он не был отправлен, поэтому на удалёнке его нет.

### Порядок восстановления

1. **Бэкап повреждённого `.git`** целиком
   (`cp -r .git <бэкапы>/git-damaged-<дата>/`) и отдельно `.git/index`.
2. Убедиться, что рабочее дерево цело и содержит нужный контент —
   оно и есть источник истины при потере коммитов.
3. Восстановить потерянные blob'ы из рабочего дерева:
   `git hash-object -w <файл>` (хеш сходится — контент тот же).
4. Переставить ref'ы на последний **проверяемый** коммит
   (`git update-ref refs/heads/master <sha-с-удалёнки>`), не откатывая
   рабочее дерево: `--hard` не использовать.
5. Восстановить remote-tracking ref (`refs/remotes/origin/master`).
6. Почистить битые reflog-записи (ссылались на утраченный `2f5c376`).
7. Сбросить битый cache-tree: `git read-tree HEAD` (индекс сбрасывается
   к дереву HEAD; затем `git add -A`, чтобы вернуть рабочее состояние).
8. Пересоздать утраченный коммит из рабочего дерева (`git add -A`,
   `git commit -F <msg>`), не забыв про `user.name`/`user.email`.
9. `git fsck --full` → пусто, `git status`/`log`/`push --dry-run` → ОК.

### Приёмка (30.09.2026)

- `git fsck --full` — **чисто**: 0 ошибок, 0 отсутствующих объектов;
- `git status` — работает, дерево чистое (кроме локального `t2.scss`);
- `git log --oneline -10` — история на месте (DEV-102 → DEV-60 → DEV-59…);
- `git push --dry-run origin master` → `2069e37..765500c` (fast-forward,
  без `--force`);
- рабочее дерево **не изменено** (`style.css` — те же 79 743 байта,
  MD5 `f8ed3986…` на дату DEV-134; после DEV-138, поднявшего версию темы
  до 1.0.78, MD5 — `62eb661b…` при том же размере).

### Уроки

- **Не удалять `.git`** при таких сбоях — сначала копия целиком.
- Потеря одного loose-объекта легко тянет за собой битые ref'ы,
  reflog и cache-tree индекса; лечить нужно всё сразу, а не только `HEAD`.
- Рабочее дерево — последний рубеж: если коммиты утрачены, контент
  восстанавливается из файлов (`hash-object -w` + новый коммит).
- `git update-ref` переписывает ref, но **не трогает** рабочее дерево —
  это безопасная замена `reset --hard` при починке истории.
