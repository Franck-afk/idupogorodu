# Раздел 2. Грабли

> Источник: бывший `.workbuddy-ai/memory/PITFALLS.md`.
> Сюда смотри **перед** тем, как чинить что-то в этом проекте.


Подробности к разделу «Ключевые грабли» в `MEMORY.md`. Читать при работе с соответствующим слоем.

### Инструменты и окружение

- **`WP_CLI` в CLI-проверках:** нельзя просто объявить константу — `class-migrations.php`
  использует `class_exists( 'WP_CLI' )` и падает. Для бутстрапа WP из CLI подставлять
  `$_SERVER['HTTP_HOST']` и `$_SERVER['REQUEST_SCHEME']`.
- **Git Bash на Windows: запись в `/tmp` и `/dev/null` через `curl -o` падает с exit 23.**
  Писать временные файлы в рабочую папку. Коварное следствие: `grep -c 'маркер' несуществующий-файл`
  молча даёт **0**, и тест «показывает», что элемента нет нигде. Проверять `exit`-код curl и
  `wc -c` файла **до** grep.
- **Cookie с `HttpOnly`** в cookie-jar пишется с префиксом `#HttpOnly_`, поэтому `grep -v '^#'`
  её удаляет — jar кажется пустым, хотя cookie есть.
- **Валидную auth-cookie админа нельзя сгенерировать из CLI:** `COOKIEHASH` считается от другого
  `siteurl`, плюс `WP_Session_Tokens::create()` пишет `REMOTE_ADDR`/`User-Agent`, и
  `is_still_valid()` отклоняет cookie из другого окружения. Для HTTP-проверок — mu-plugin авто-логина.
- `wp_redirect()` / `wp_safe_redirect()` **не вызывают `exit`** — `exit` пишет вызывающий код.
  Перехватить редирект в тестах можно фильтром `wp_redirect`.
- **`git apply` в Git Bash: `can't open patch '/d/…': No such file or directory`**, хотя файл на
  месте. Git — нативная программа Windows и после смены каталога не понимает POSIX-пути.
  Конвертировать: `cygpath -m "$1"` (с проверкой `command -v cygpath` для Linux).
- **`git clone` из-под песочницы: `detected dubious ownership`** (разные SID). Обход на один
  вызов — `git -c safe.directory='*' clone …`.
- **`grep -c $'\r' файл` в Git Bash врёт** (даёт ≈ число строк) даже на файле без CRLF.
  Считать переводы строк только через `tr -cd '\r' < файл | wc -c`.
- **`composer install` под песочницей: «The APPDATA or COMPOSER_HOME environment variable must be
  set»** — песочница вырезает переменные окружения. Перед вызовом экспортировать `APPDATA`,
  `COMPOSER_HOME`, `COMPOSER_CACHE_DIR`, `LOCALAPPDATA`.
- **Сверять пакеты vendor с эталоном только по версии из `composer.lock`.** В кэше Composer
  (`%LOCALAPPDATA%\Composer\files\<vendor>\<pkg>\<hash>.zip`, верхний каталог архива —
  `vendor-pkg-<shorthash>`) лежат несколько версий; сравнение не с той даёт сотни ложных
  «различий» (у `squizlabs/php_codesniffer` — 864 вместо 0).
- **Не судить о «штатности» кода по рабочей копии.** Вывод «это upstream-код, а не патч»,
  сделанный grep-ом по уже пропатченному дереву, оказался ложным (DEV-54). Нужен
  иммутабельный эталон — распакованный дистрибутив из кэша.
- **Генерация патча через Python `difflib`:** многострочный добавленный комментарий нельзя
  передавать **одним** элементом списка — `+` получит только первая строка, hunk разъедется
  (`corrupt patch … :9`). Каждую строку — отдельным элементом.
- **`vendor/bin/phpcs` из Git Bash: `env: 'php': No such file or directory`, код 127.**
  Это shell-скрипт с `#!/usr/bin/env php`, поэтому PHP ищется через `PATH`; полный путь
  к `php.exe` в самой команде не помогает. Лечение:
  `export PATH="/d/laragon/bin/php/php-8.2.29-nts-Win32-vs16-x64:$PATH"`.
- **Песочница ассистента отбрасывает записи в `.git/refs/remotes/**` и создание НОВЫХ
  ПОДКАТАЛОГОВ в `.git/refs/`.** `git fetch` печатает «[new branch] main -> origin/main»,
  `git update-ref` возвращает 0, но файлы ref не появляются и `git status` показывает `[gone]`;
  ветка со слэшем (`tmp/origin-main`) молча не создаётся — `git branch` возвращает 0, а `git log`
  её не видит, тогда как `tmpmain` создаётся нормально. **Рабочие ветки называть без слэша.**
  На реальность операций с remote не влияет: проверять результат сетевым `git ls-remote origin`,
  а не локальными ссылками. Лечится одним `git fetch origin` в обычном терминале.
- **Упавший `git fetch` обнуляет `.git/FETCH_HEAD`** (0 байт). После сбоя ссылаться на
  `FETCH_HEAD` нельзя — использовать SHA коммита (объекты из прошлого удачного fetch остаются
  в базе) или распакованный bundle.
- **`git diff --name-status` по умолчанию склеивает переименования** и может спрятать файл
  из выборки. Пример (DEV-59): `plugins/idpg-event-import/phpunit.xml.dist` был спарен с
  `plugins/idpg-auth/phpunit.xml.dist` в пару `R`, из-за чего список «только `D`» дал 28 вместо 29.
  Для сравнения составов — `--no-renames`, и перекрёстно сверять с подсчётом по деревьям
  (`comm -13` по двум `git ls-tree -r --name-only`).
- **`git bundle create` с POSIX-путём:** `Unable to create '…bundle.lock': No such file or
  directory`. Git — нативная программа Windows, путь `/d/...` не понимает; конвертировать
  через `cygpath -m`. (Та же природа, что у `git apply`.)

- **`git check-ignore` — два независимых источника вранья. Проверять только `-q`.**

  1. **По умолчанию он смотрит в индекс.** Git **никогда не игнорирует уже отслеживаемые
     файлы**, и `check-ignore` это учитывает: для tracked-пути он отвечает «не игнорируется»,
     даже если правило матчит. Истину по паттернам даёт `--no-index`.
  2. **`-v` возвращает exit 0, если сматчился ЛЮБОЙ паттерн — включая отрицательный `!`.**
     Для re-include-путей `-v` печатает сам `!`-паттерн и отдаёт 0, что читается как
     «игнорируется», хотя файл как раз **не** игнорируется. Пример после DEV-60:
     ```
     $ git check-ignore -v --no-index plugins/idpg-core/assets/vendor/iconify/iconify.min.js
     .gitignore:69:!plugins/idpg-core/assets/vendor/**   …/iconify.min.js
     $ echo $?   # 0  ← ЛОЖЬ: это «паттерн сматчился», а не «игнорируется»
     $ git check-ignore -q --no-index <тот же путь>; echo $?   # 1  ← правда
     ```

  **Рабочий рецепт:** для булева ответа — `git check-ignore -q [--no-index] <path>`
  (0 = игнорируется, 1 = нет). `-v` брать только чтобы узнать, **какой** паттерн сматчился,
  и не читать его exit-код как вердикт.

  **Практический вывод:** файл может быть **опубликован в репозитории и при этом считаться
  игнорируемым** — он выживает лишь как tracked; удалили и снова `git add` → потерян молча.
  Для таких путей нужен явный re-include (`!path`), как в `21bc289` и DEV-60.
  **Настоящая проверка re-include** — не `check-ignore`, а временный индекс: убрать пути из
  индекса и добавить заново **без `-f`**:
  ```bash
  export GIT_INDEX_FILE="D:/…/testindex"   # Windows-путь, git — нативная программа
  git read-tree HEAD
  git rm --cached -r -q <dirs> && git add <dirs>   # без -f; вернулись = re-include работает
  ```

### Доказательство «merge ничего не теряет» для несвязанных историй

Прежде чем звать владельца решать судьбу слияния, конфликт и потери считаются **без правок
рабочего дерева**:

1. **Поверхность конфликта.** `git merge-tree --write-tree --allow-unrelated-histories
   --name-only <ours> <theirs>` — печатает конфликтующие пути и `CONFLICT (add/add)` строки,
   exit 1. Ничего не трогает. (Без `--allow-unrelated-histories` merge-tree откажется.)
2. **Что вообще расходится:** `git diff --name-status --no-renames <theirs> <ours>`
   → `A` = только наши, `M` = разные версии (= кандидаты в конфликт).
3. **Есть ли у них файлы, которых нет у нас:** `comm -23 <(git ls-tree -r --name-only theirs|sort)
   <(…ours|sort)` — пусто ⇒ наше дерево строго надмножество, терять нечего.
4. **Не теряем ли строки:** `git diff -U0 theirs ours` → `grep -P '^-[^-]' | sort | uniq -c`
   просмотреть **каждое** удаление вручную. Формальные удаления (переписанный `.gitignore`,
   форматирование) отделяются от функциональных.
5. **Финальное доказательство — хеш дерева.** Пробный merge с авто-разрешением в нашу пользу:
   `git merge -X ours --allow-unrelated-histories --no-commit <theirs>`, затем сравнить
   `git write-tree` (индекс = результат merge) с `git rev-parse master^{tree}`.
   **Совпадение хешей = merge побайтово равен нашему состоянию**, потерь нет.
   Откат: `git merge --abort` + `git reset --hard master`.

`-X ours` на add/add разрешает конфликт целиком в нашу пользу — если шаг 4 показал, что наши
версии новее, ручное разрешение не нужно вовсе.

### Тесты, проверяющие привязку хуков темы (`has_action` / `has_filter`)

**Симптом:** тест падает с `Failed asserting that false is not false`, хотя
`grep` в исходнике показывает нужный `add_action`. Исходники верны — врёт окружение.

**Причина.** `WP_UnitTestCase::tear_down()` вызывает `_restore_hooks()`
(`wordpress-develop/tests/phpunit/includes/abstract-testcase.php`), который откатывает
`$GLOBALS['wp_filter']` к снимку, снятому в **первом** `set_up()`
(`if ( ! self::$hooks_saved ) { $this->_backup_hooks(); }`).
Если тема подключается внутри теста (`require_once functions.php` после снимка),
её хуки в снимок не попадают и **исчезают после первого теста**. `require_once`
идемпотентен → `add_action()` повторно не выполняется → в последующих тестах
`has_action()` / `has_filter()` честно возвращают `false`.

**Лечение:** перерегистрировать проверяемые привязки в `setUp()` **и** не выходить
из `setUp()` раньше времени по `function_exists()`:

```php
protected function setUp(): void {
	parent::setUp();
	if ( ! function_exists( 'idpg_core_create_organizer_page' ) ) {
		/* ...подключение темы: фильтры theme_root/stylesheet_root/template_root,
		   register_theme_directory(), switch_theme(), require_once functions.php */
	}
	$this->restore_theme_hooks();   // всегда, а не только при подключении темы
}

protected function restore_theme_hooks() {
	if ( ! has_action( 'after_setup_theme', 'idpg_core_create_organizer_page' )
		&& ! has_action( 'after_switch_theme', 'idpg_core_create_organizer_page' ) ) {
		add_action( 'after_setup_theme', 'idpg_core_create_organizer_page' );
	}
	// ...то же для каждого проверяемого фильтра
}
```

Условие «если ещё нет привязки» делает перерегистрацию идемпотентной: в первом
тесте она ничего не делает (хук ещё жив), в последующих — восстанавливает.
Эталон — `plugins/idpg-core/tests/test-organizer-page-creation.php`.

`themes/idpg_core/bin/revert-probe-organizer-ui.mjs` применяет мутации к рабочему
дереву и откатывает их из резервной копии. Грабли:

- **Прерванный прогон оставляет мутацию в коде.** `Ctrl+C` или закрытие
  терминала убивали процесс до финального `restore()`. Позже «зелёная» приёмка
  проверяла сломанный файл, и хуже всего: следующие прогоны копировали в
  backup **уже сломанное** состояние, поэтому поломка воспроизводилась сама.
  Лечится `process.on('exit'|'SIGINT'|'SIGTERM', finish)` плюс `try/finally`.
  После любой пробы проверять остатки мутаций отдельным проходом.
- **Критерии надо усиливать, а не подгонять под мутацию.** Первая версия
  критерия «контракт `data-idpg-*`» считала атрибуты только в `organizer.js` и
  не замечала переименование атрибута в шаблоне. Правильно: объединение всех
  скриптов кабинета (три файла) против разметки, причём 10 атрибутов скрипты
  создают сами (`setAttribute` и HTML-фрагменты) — их нет в разметке законно.
- **Мутация, которая не применилась, выглядит как «критерий слабый».** Здесь
  подмена искала строку `padding: var(--idpg-space-lg);`, которой в файле нет
  (значение составное). Прежде чем править критерий — проверить, что мутация
  вообще что-то меняет.
- **PHPCS CSV отдаёт `Type` в нижнем регистре** (`error`, не `ERROR`). Сравнение
  по `,ERROR,` даёт «0 ошибок» на файле с 39 нарушениями. Разбирать CSV с учётом
  кавычек, а не `match('ERROR')`.
- **`execFileSync` на Windows требует `shell: true`** для `npm`/`.cmd`, иначе
  ENOENT и неверный код возврата. С `shell: true` нельзя передавать inline-код
  с пробелами и `||` — cmd его разорвёт; такие обходы делать внутри процесса.

### Порядок присваиваний в `organizer.js`: `var` до раннего `return` (DEV-196)

- **Присваивание `var` после вызова инициализатора не поднимется.** Объявления
  функций поднимаются, значения — нет. Если `initVenues()` вызывается в начале
  IIFE, а `VENUE_COLUMNS = [...]` стоит ниже по файлу, то при мгновенном ответе
  REST (кеш, Service Worker, тестовый стенд с синхронным `fetch`) строки таблицы
  строятся раньше присваивания и получают `undefined`. Симптом: `undefined is not
  iterable` / `Cannot read properties of undefined (reading '0')`, причём только
  в тестах — в браузере с настоящим `fetch` баг не воспроизводится.
- В `organizer.js` это уже второй случай: `VENUE_TYPE_LABELS` вынесен к
  началу файла по той же причине, и там стоит предупреждение. Новые табличные
  константы (`EVENT_COLUMNS`, `VENUE_COLUMNS`) помещены туда же.
- **Проверять такие места только стендом с синхронным `fetch`.** Обычный прогон
  в браузере этот класс дефектов пропускает.

### PHPUnit: запуск, MySQL и грабли (DEV-196, 01.10.2026; DEV-205, 02.10.2026)

### Отключение роутера `/organizer/*`: 301 вместо 404 (DEV-235, 07.10.2026)
